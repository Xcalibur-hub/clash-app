# First hosted staging creation checklist

Preparation only. See [Step 5U](PHASE_11_HOSTED_EXECUTOR_PREPARATION_5U.md) and [Step 5T](PHASE_11_HOSTED_STAGING_READINESS_5T.md). No project creation, credential generation or connection is authorized by these documents.

## Decisions requiring the owner

1. Which Supabase organization owns the new, disposable-to-start **CLASH staging** project, and which person owns billing/security recovery?
2. Which region meets tester latency/data-location needs, and what monthly budget/plan limit is approved? The Step 5W executor supports the approved shared session pooler on IPv4; no paid IPv4 add-on is needed. Confirm the Dashboard session endpoint, not the transaction endpoint.
3. Who is the named deployment operator/security reviewer, and which private secret store/access window is approved? Give agents task-scoped staging access only; no production keys or credentials in chat/GitHub.
4. Approve creating **one new project** and **one read-only preflight** against its exact Dashboard-confirmed reference, with stop-on-first-failure and no repair. This is distinct from later migration/extension/fixture authorization.

## Engineering prerequisites ? no extra product decisions needed now

- Reverify frozen seal/hashes, reviewed artifact and offline tests; build the pinned separate executor. Confirm the new project has no real users, data, external app origin or production redirect.
- Record project/region/owner and approved CA fingerprint outside Git; secret password stays in the approved secret store. Verify private Windows ACLs. No linked-project defaults or inherited backend credentials.
- The first probe must use verified TLS and the exact approved direct or session-pooler hostname, routing username and database. Missing connectivity, certificate, managed identity or required capability stops the attempt; never use plaintext or another existing project.
- Keep testers, SMTP delivery, outbound hooks and app builds disabled until backend validation. SMTP credentials, redirects, Storage/Realtime publication review, secrets/Edge key compatibility, backups and staging app allowlists can be finalized after preflight, before any relevant flow is enabled.
- Request separate approval for managed extension prerequisites and migration execution after reviewing preflight; separate approval again for scheduler pause, fixture-producing/concurrency tests and bounded cleanup. Empty-project attestation is not sufficient permission to execute them.
- Do not merge source PRs, reset databases or treat the existing-local Step 4C block as lifted. Android Step 2F remains deferred.

## Step 5W supported creation and first-preflight procedure

**Preparation only; obtain fresh target-specific authorization before executing.** Step 5V created zero projects. The previously discovered organization/Free quote are prior evidence, not current quota or capacity guarantees.

1. Owner verifies the organization, Free/no-charge eligibility and Mumbai availability in Supabase Dashboard. Stop for any paid plan/add-on, unavailable region or ambiguous target. Do not use the automatic create-project connector: its password handoff is unverified.
2. Owner chooses one fresh strong per-project database password, retained privately in their approved protected password manager or operator memory until secure storage. Do not use a password generated by an interface that will not safely reveal/capture it. If an approved private retention method is not available, stop **before creation**. Create exactly one empty `clash-staging` project in Dashboard only after separate approval. Do not reuse passwords or create a second project after an ambiguous outcome.
3. Record the new reference, organization, plan and region independently. From that project's **Connect > Session pooler** panel copy only the host/port/username metadata, not a password-bearing URI. Verify port 5432 and username `postgres.<exact-ref>`. Never synthesize the host from Mumbai or another region. Leave apps/testers/signup/production integrations disconnected.
4. Under the named operator's normal interactive Windows account, set `credential_source: windows-credential-manager` in the nonsecret config. Run the separately authorized `store-credential:<ref>` command in the executor README; enter the already chosen password only in its native dialog, keeping username `postgres`. No shell argument, transcript, plaintext file or clipboard automation is involved. Storage failure requires owner recovery, never automatic project deletion, credential reset or recreation. This tool refuses overwriting an existing entry; rotation needs separate review.
5. Set `connection_mode: session-pooler` and the exact approved `pooler_host`. Verify a trusted CA bundle/fingerprint appropriate to the pooler certificate; direct-project CA certificates are not automatically interchangeable. All other artifact/suite hashes stay frozen. Choose an absolute fresh evidence directory under private NTFS ACLs. Use a clean process with no inherited PG/Supabase/backend overrides or password environment variable.
6. After explicit authorization for **one read-only preflight** on this reference, run only `--mode preflight --authorize preflight:<ref> --config <nonsecret-config>`. Certificate chain/hostname verification, database/login role, backend continuity and all read-only checks must succeed. Stop on the first error without fallback, target changes, privilege repair or rerun. Inspect partial `preflight.json` and `outcome.json` privately; sanitize before sharing.
7. Review installed/available extensions (pgcrypto, PostGIS, pg_cron, pgTAP, dblink), owners, role memberships/restricted file privileges, managed schemas/publication, cron preload/jobs, empty application-object/data checks and migration ledger. Missing extension installation privileges, incompatible owners/versions or vendor schema differences require separate decisions. No extension, job or policy is changed by preflight.
8. Request **separate** migration/prerequisite authorization only after those results are reviewed. Concurrency/fixture SQL suites, active scheduler management and cleanup each require their own scope. Step 4C remains BLOCKED against the existing local database; Android Step 2F stays DEFERRED.

The shared hostname's TLS certificate identifies the pooler, not a particular tenant. Project binding comes from the independently verified Dashboard endpoint, exact project-qualified routing username, fresh project-specific password and checked backend role/database. There is no invented SQL project-reference setting. This preparation does not claim a live identity or TLS verification has occurred.
