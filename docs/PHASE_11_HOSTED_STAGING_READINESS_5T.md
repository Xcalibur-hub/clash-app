## Step 5S TLS investigation — offline only

Confirmed runtime evidence: CLI 2.40.7 reported a remote connection and `tls error (server refused TLS connection)` against the disposable loopback endpoint; supplied URL included `sslmode=disable`. Application migration execution never began.

Tagged source provides a strong explanation: [migration up](https://github.com/supabase/cli/blob/v2.40.7/internal/migration/up/up.go) calls `ConnectByConfig`. In [connect.go](https://github.com/supabase/cli/blob/v2.40.7/internal/utils/connect.go), the remote branch reconstructs a URL using host/user/port/database and RuntimeParams, without serializing TLSConfig; it then filters non-TLS fallback configurations. Local detection also requires matching configured port. A supplied SSL option represented as TLS configuration can therefore be lost during reconstruction, leaving TLS attempted with no plaintext fallback. This is source-based explanation consistent with the observed failure; binary-level effective options were not captured, and no runtime reproduction occurred in Step 5T.

Bounded future diagnostic proposal: inspect pinned URL parsing and connect serialization with a pure in-memory unit test (no socket/DB), comparing disable/require/verify-full, CA path, host and nondefault port. Confirm whether the exact binary matches tagged source; redact generated/reconstructed URLs because that helper can serialize passwords. Review a supported newer CLI's source/tests before pinning any replacement. For hosted deployment require verified certificate/hostname TLS, not the local disable setting; accept one separately authorized read-only connection probe on the **new approved target only**, with a short timeout and no migration side effects. Stop on TLS/identity/CA mismatch; do not change server SSL enforcement, retry with insecure modes or switch targets. No local retry is recommended.

[Hosted TLS guidance](https://supabase.com/docs/guides/platform/ssl-enforcement) recommends certificate/hostname verification. CLI 2.40.7's handling must be established before asserting it preserves verify-full/CA settings. Hosted TLS support alone does not prove this client verifies identity. The preferred next checkpoint is file-only hosted executor/test-adapter preparation, followed by separately authorized new-project preflight and validation; no immediate deployment.
